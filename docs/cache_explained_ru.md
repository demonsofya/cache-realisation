## 1. Общий принцип и интерфейс

### 1.1. Что именно моделирует программа

Есть последовательность запросов к данным, например `1 2 3 1 4 2`. Число — это **ключ**: идентификатор запрашиваемого объекта. У кэша есть ограничение `capacity`, то есть максимальное количество одновременно хранимых объектов.

При каждом запросе возможны два результата:

- **Попадание, hit:** значение уже находится в кэше. Загружать его заново не нужно.
- **Промах, miss:** значения в кэше нет. Оно загружается, а при заполненном кэше приходится выбрать объект для вытеснения.

Политика кэширования отвечает прежде всего на вопрос: **какой объект удалить, чтобы сохранить более полезные данные?**

В проекте размер измеряется количеством объектов, а не байтами. Начальное состояние кэша пустое. Время загрузки, задержки уровней, размер значения в байтах и операции записи не моделируются. Поэтому число попаданий позволяет сравнивать поведение политик, но само по себе не измеряет ускорение программы.

### 1.2. Что означают параметры шаблона

Классы LRU, LFU, 2Q, ARC и LIRS имеют параметры `T` и `KeyT`:

- `KeyT` — тип ключа, по умолчанию `size_t`;
- `T` — тип хранимого значения.

Например, в `lru_cache_t<int, int>` и ключ, и значение имеют тип `int`. Ключ и значение вообще могут различаться: номер страницы и её содержимое — разные сущности. Но в текущем симуляторе многоуровневого кэша принято упрощение **значение равно ключу**.

### 1.3. Что делает lookup_update

Основной метод принимает ключ и функцию загрузки `slow_get_value`. Он одновременно проверяет наличие значения, обновляет служебные структуры и при необходимости вставляет данные. Возвращается `bool`, а не само значение:

- `true` — значение уже было в кэше;
- `false` — значения не было до текущего обращения.

Поэтому выражение `hits += cache.lookup_update(key, slow_get_value)` корректно: `true` добавляет единицу, `false` — ноль. После промаха значение может уже находиться в кэше, но результат текущего запроса всё равно остаётся промахом.

`slow_get_value` — переданный вызывающей стороной объект, который можно вызвать как функцию. Имя означает «медленно получить значение», но в симуляторе он обычно просто возвращает ключ. На обычном попадании загрузчик не вызывается.

Особый случай — нулевая ёмкость:

Источник: [include/lru_cache.hpp, строки 15–16](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/include/lru_cache.hpp#L15-L16).

```cpp
        if (capacity_ == 0)
            return false;
```

Такой кэш всегда возвращает `false` и даже не вызывает загрузчик. Это важно для построения иерархии: переход на следующий уровень должен работать и при нулевом размере верхнего кэша.

### 1.4. Почему список дополняется хеш-таблицей

В нескольких реализациях используются одновременно `std::list` и `std::unordered_map`.

Список хранит **порядок**: кто недавно использовался, кто пришёл раньше, кто первым будет удалён. Сам по себе он неудобен для поиска ключа: приходится идти по элементам.

Хеш-таблица обеспечивает быстрый поиск по ключу. Если её значение — итератор списка, после поиска сразу известно, какой узел нужно передвинуть или удалить.

`splice` переносит существующий узел списка. Например, перенос в `begin()` означает «сделать первым». Узел не нужно заново создавать, а итератор на перемещённый узел остаётся действительным. Это позволяет обновлять порядок без повторного поиска.

### 1.5. Значение и история — разные вещи

В 2Q, ARC и LIRS могут сохраняться ключи уже вытесненных объектов. Такая запись называется **историей** или **ghost-записью**. Она сообщает: «этот ключ недавно встречался», но не содержит доступного значения.

Поэтому обнаружение ключа в истории — **промах**. История помогает принять решение о размещении и вытеснении, но не заменяет загрузку данных. Число записей истории также нельзя считать числом реально хранимых объектов.

## 2. LRU: давность последнего обращения

**LRU — Least Recently Used:** вытесняется объект, к которому дольше всего не обращались.

Идея: если данные понадобились недавно, они могут понадобиться снова. Важна давность последнего обращения, а не общее число обращений за всё время.

### 2.1. Структуры данных

Источник: [include/lru_cache.hpp, строки 72–75](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/include/lru_cache.hpp#L72-L75).

```cpp
    std::list<std::pair<KeyT, T>> counter_;
    using CounterIter = typename std::list<std::pair<KeyT, T>>::iterator;

    std::unordered_map<KeyT, CounterIter> cache_;
```

В `counter_` находятся пары «ключ — значение». Несмотря на имя `counter_`, здесь нет числового счётчика частоты. Список задаёт порядок давности:

- в начале — объект, к которому обращались последним;
- в конце — объект, к которому дольше всего не обращались.

`cache_` хранит соответствие «ключ — итератор в `counter_`». Значение объекта лежит в списке, а таблица помогает найти его узел.

### 2.2. Попадание

Источник: [include/lru_cache.hpp, строки 18–26](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/include/lru_cache.hpp#L18-L26).

```cpp
        auto cache_iter = cache_.find(key);
        if (cache_iter != cache_.end()) {

            auto counter_iter = cache_iter->second;
            counter_.splice(counter_.begin(), counter_, counter_iter);

            ON_DEBAG(std::cout << "Found elem " << counter_iter->first << "\n"; print_cache(););

            return true;
```

После успешного `find` программа берёт итератор узла и переносит этот узел в начало списка. Остальные узлы сохраняют взаимный порядок. Затем возвращается `true`.

Количество элементов не меняется. Значение не загружается повторно. Меняется только информация о давности использования.

### 2.3. Промах и вытеснение

Источник: [include/lru_cache.hpp, строки 29–45](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/include/lru_cache.hpp#L29-L45).

```cpp
        T value = slow_get_value(key);
        if (size_ == capacity_) {

            cache_.erase(counter_.back().first);

            ON_DEBAG(std::cout << "Deleting from counter and cache elemet "
                               << counter_.begin()->first << "\n");

            counter_.pop_back(); // last recently used element

        } else {

            size_++;
        }

        counter_.emplace_front(std::make_pair(key, value));
        cache_[key] = counter_.begin();
```

Сначала загружается значение. Если кэш заполнен, из таблицы удаляется ключ последнего узла, затем удаляется сам узел. Порядок этих двух действий важен: пока узел существует, из него можно прочитать ключ.

Если место было свободно, увеличивается `size_`. При замене одного объекта другим размер не увеличивается.

Новая пара вставляется в начало списка, а в таблицу записывается итератор нового узла.

### 2.4. Пример по шагам

Ёмкость `3`, запросы `1 2 3 1 4 2`. В списке слева находится самый недавно использованный ключ.

| Запрос | Результат | Кого вытеснили | Список после запроса |
|---|---|---|---|
| 1 | Промах | — | `1` |
| 2 | Промах | — | `2, 1` |
| 3 | Промах | — | `3, 2, 1` |
| 1 | Попадание | — | `1, 3, 2` |
| 4 | Промах | 2 | `4, 1, 3` |
| 2 | Промах | 3 | `2, 4, 1` |

Итог: **1 попадание, 5 промахов**.

### 2.5. Когда правило помогает и мешает

LRU хорошо соответствует работе с недавно открытыми страницами или небольшим текущим набором объектов. При изменении интересов старые данные постепенно исчезают.

Однако длинное последовательное чтение новых объектов может вытеснить весь полезный набор. У LRU нет отдельной защиты для данных, которые раньше использовались очень часто.

## 3. LFU: число обращений

**LFU — Least Frequently Used:** вытесняется объект с наименьшим числом обращений среди текущих объектов кэша.

В этой реализации частота начинается с `1` при вставке. После вытеснения частота ключа не сохраняется: при новом поступлении он снова начинает с единицы.

### 3.1. Как хранятся данные

`cache_` — таблица «ключ — значение». `counter_` — список пар «ключ — частота», отсортированный по неубыванию частоты.

Это отличается от LRU: таблица не содержит итератор в список. Поэтому после нахождения значения нужно отдельно найти запись частоты.

### 3.2. Попадание и обновление частоты

Источник: [include/lfu_cache.hpp, строки 22–34](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/include/lfu_cache.hpp#L22-L34).

```cpp
            auto curr_it = counter_.begin();
            for (; curr_it != counter_.end(); curr_it++) {
                if (curr_it->first == key)
                    break;
            }

            ++(curr_it->second);

            auto next_it = std::next(curr_it);
            while (next_it != counter_.end() && next_it->second < curr_it->second)
                next_it++;

            counter_.splice(next_it, counter_, curr_it);
```

Первый цикл ищет ключ в списке. Затем частота увеличивается на единицу. Второй цикл проходит вперёд, пока встречает элементы с меньшей частотой. `splice` перемещает обновлённый узел перед найденной позицией.

Так сохраняется порядок по частоте. Условие использует строгое `<`, поэтому узел не проходит мимо элементов с равной новой частотой.

### 3.3. Что удаляется при промахе

Источник: [include/lfu_cache.hpp, строки 67–71](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/include/lfu_cache.hpp#L67-L71).

```cpp
        auto deliting_elem = counter_.begin();
        cache_.erase(deliting_elem->first);

        *deliting_elem = {key, static_cast<size_t>(1)}; // canging counter_
        cache_[key] = value;                            // changing cache_
```

При полном кэше удаляется ключ первого узла списка — у него минимальная частота. Сам узел переиспользуется: в него записываются новый ключ и частота `1`.

Если кэш ещё не заполнен, новый узел с частотой `1` добавляется в начало списка.

**При равных частотах здесь не применяется отдельное правило LRU.** Результат зависит от текущего положения узлов. Например, после первых запросов `1 2 3` список имеет вид `3:1, 2:1, 1:1`: следующим кандидатом на удаление является `3`, хотя он поступил последним.

### 3.4. Пример на той же последовательности

Ёмкость `3`, запросы `1 2 3 1 4 2`. Запись `ключ:частота` показывает список от начала к концу.

| Запрос | Результат | Список после запроса |
|---|---|---|
| 1 | Промах | `1:1` |
| 2 | Промах | `2:1, 1:1` |
| 3 | Промах | `3:1, 2:1, 1:1` |
| 1 | Попадание | `3:1, 2:1, 1:2` |
| 4 | Промах, вытеснен 3 | `4:1, 2:1, 1:2` |
| 2 | Попадание | `4:1, 2:2, 1:2` |

Итог: **2 попадания, 4 промаха**. Здесь LFU сохранил ключ `2`, который LRU вытеснил. Это результат конкретной последовательности и правила разрешения равных частот, а не доказательство преимущества LFU на любых данных.

### 3.5. Ограничения именно этой реализации

Частоты не уменьшаются со временем. Если пользователь долго работал с одним набором, а затем перешёл на другой, старые популярные ключи могут долго занимать кэш.

Кроме того, попадание может потребовать прохода по списку длины до `capacity`: сначала поиск узла, затем поиск новой позиции. Поэтому для этого LFU нельзя заявлять постоянное время на любой запрос только на основании наличия хеш-таблицы.

## 4. 2Q: новые и повторно востребованные данные

**2Q — Two Queues:** политика отделяет недавно поступившие данные от объектов, которые показали повторную востребованность. В проекте есть три структуры, поскольку одна из них хранит только историю.

### 4.1. Назначение структур

| Структура | Что хранит | Порядок | Назначение |
|---|---|---|---|
| `A1in` | Ключи и значения новых объектов | FIFO: удаление с конца | Проверить, будут ли данные востребованы снова |
| `A1out` | Только ключи, вытесненные из A1in | История недавних вытеснений | Узнать повторное обращение после удаления |
| `Am` | Ключи и значения повторно востребованных объектов | LRU | Сохранить полезные данные дольше |

Общее число значений в `A1in` и `Am` ограничено `capacity_`. История `A1out` содержит дополнительные ключи, а не дополнительные значения.

### 4.2. Параметры kin и kout

Источник: [include/twoq_cache.hpp, строки 7–11](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/include/twoq_cache.hpp#L7-L11).

```cpp
    twoq_cache_t(size_t capacity)
        : capacity_(capacity),
          kin_(capacity == 0 ? 0 : std::max<size_t>(1, capacity / 4)),  // kin ~ 25% capacity
          kout_(capacity == 0 ? 0 : std::max<size_t>(1, capacity / 2)), // kout ~ 50% capacity
          am_cache_(capacity) {}
```

Для положительной ёмкости:

- `kin_ = max(1, capacity / 4)`;
- `kout_ = max(1, capacity / 2)`.

Деление целочисленное. При ёмкости `3` получаются `kin_ = 1` и `kout_ = 1`.

Комментарий у поля `kin_` в коде называет его максимальным размером A1in, но фактическое условие в `reclaim()` использует его как **порог выбора очереди для вытеснения**. A1in может стать больше `kin_`, особенно при начальном заполнении, когда Am ещё пуст.

Внутренний LRU `am_cache_` создаётся с ёмкостью всего кэша. Это не означает, что Am получает ещё столько же свободных мест: общий размер контролируется внешним `size_` и функцией `reclaim()`.

### 4.3. Что происходит при разных запросах

При попадании в Am вызывается его `lookup_update`: объект перемещается в начало LRU-списка, возвращается `true`.

Для A1in и истории логика другая:

Источник: [include/twoq_cache.hpp, строки 25–38](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/include/twoq_cache.hpp#L25-L38).

```cpp
        auto a1in_iter = a1in_cache_.find(key);
        if (a1in_iter != a1in_cache_.end())
            return true; // if in a1in - do nothing

        auto a1out_iter = a1out_cache_.find(key);
        if (a1out_iter != a1out_cache_.end()) { // if in a1out - move to am
            a1out_counter_.erase(a1out_iter->second);
            a1out_cache_.erase(a1out_iter);

            reclaim();

            am_cache_.lookup_update(key, slow_get_value);
            size_++;
            return false;
```

Если ключ находится в A1in, возвращается `true`, но порядок не меняется и перевода в Am нет. Поэтому несколько близких обращений к только что загруженному объекту ещё не дают ему статус Am.

Если ключ есть в A1out, значение уже удалено. История стирается, освобождается место, значение загружается во внутренний LRU Am. Возвращается `false`.

Совсем новый ключ после загрузки и освобождения места попадает в начало A1in.

### 4.4. Как reclaim выбирает жертву

Источник: [include/twoq_cache.hpp, строки 55–67](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/include/twoq_cache.hpp#L55-L67).

```cpp
    void reclaim() {
        if (size_ < capacity_)
            return;

        if ((!a1in_counter_.empty() && a1in_counter_.size() > kin_) || am_cache_.counter_.empty()) {

            KeyT old_key = a1in_counter_.back().first;

            a1in_cache_.erase(old_key);
            a1in_counter_.pop_back();

            a1out_counter_.emplace_front(old_key);
            a1out_cache_[old_key] = a1out_counter_.begin();
```

Если есть свободное место, функция сразу заканчивается. Иначе:

1. Если A1in больше порога `kin_` либо Am пуст, удаляется самый старый объект A1in. Его ключ переносится в A1out.
2. Если размер A1out превысил `kout_`, из её конца удаляется самая старая запись истории.
3. В другой ветке вытесняется наименее недавно использованный объект Am. В A1out он не переносится: эта история относится к A1in.

После удаления значения общий `size_` уменьшается; вставка нового значения позже увеличит его обратно.

### 4.5. Пример, показывающий роль истории

Ёмкость `3`, запросы `1 2 3 1 4 1 1`. В каждой очереди слева начало.

| Запрос | Результат | A1in | A1out: только история | Am |
|---|---|---|---|---|
| 1 | Промах | `1` | — | — |
| 2 | Промах | `2, 1` | — | — |
| 3 | Промах | `3, 2, 1` | — | — |
| 1 | Попадание в A1in | `3, 2, 1` | — | — |
| 4 | Промах | `4, 3, 2` | `1` | — |
| 1 | Промах, найден в A1out | `4, 3` | `2` | `1` |
| 1 | Попадание в Am | `4, 3` | `2` | `1` |

Итог: **2 попадания, 5 промахов**. На четвёртом запросе ключ `1` не становится первым в A1in, поэтому следующий новый объект всё равно вытесняет его.

Такое разделение помогает ограничивать влияние однократного сканирования. При этом защита зависит от размеров очередей и расстояния между повторными обращениями: ключ может успеть исчезнуть и из истории.

## 5. ARC: изменение баланса между группами

**ARC — Adaptive Replacement Cache:** политика меняет соотношение между недавно появившимися и повторно использованными данными, наблюдая за обращениями к истории вытеснений.

### 5.1. Четыре списка

| Список | Содержимое | Значение присутствует? |
|---|---|---|
| `T1` | Недавно загруженные объекты без повторного попадания в текущем пребывании | Да |
| `T2` | Объекты, повторное использование которых уже выявлено | Да |
| `B1` | История вытеснений из T1 | Нет |
| `B2` | История вытеснений из T2 | Нет |

В T1 и T2 хранятся пары «ключ — значение», в B1 и B2 — только ключи. Для каждого списка есть хеш-таблица с итераторами.

`p_` — целевой размер T1, от `0` до `capacity_`. Это параметр выбора при вытеснении, а не требование, чтобы текущий размер T1 всегда был точно равен `p_`.

### 5.2. Попадания в значения

Если ключ найден в T1, программа удаляет его узел из T1 и вставляет пару в начало T2. Повторное обращение показало, что объект полезен не только при первой загрузке.

Если ключ уже находится в T2, его узел перемещается в начало T2 через `splice`.

Оба случая возвращают `true` и не вызывают загрузчик. В отличие от LFU, T2 не сортируется по числу обращений: там важен порядок недавнего использования.

### 5.3. Зачем менять p

Если пользователь запросил объект из B1, недавно удалённые данные T1 снова понадобились. Алгоритм увеличивает целевой размер T1:

Источник: [include/arc_cache.hpp, строки 82–87](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/include/arc_cache.hpp#L82-L87).

```cpp
        if (b1_iter != b1_cache_.end()) {
            size_t delta = std::max<size_t>(1, b2_counter_.size() / b1_counter_.size());

            p_ = std::min(capacity_, p_ + delta);

            replace(key);
```

Если запрос попал в B2, снова понадобился объект из группы повторно используемых данных. Целевой размер T1 уменьшается, оставляя больше предпочтения T2:

Источник: [include/arc_cache.hpp, строки 102–107](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/include/arc_cache.hpp#L102-L107).

```cpp
        if (b2_iter != b2_cache_.end()) {
            size_t delta = std::max<size_t>(1, b1_counter_.size() / b2_counter_.size());

            p_ = (delta > p_) ? 0 : p_ - delta;

            replace(key);
```

Деление здесь целочисленное. Минимальный шаг изменения — `1`; соотношение размеров историй может сделать его больше. Деления на ноль в этих ветках нет: выполнение ветки означает, что в соответствующем списке уже найден хотя бы один ключ.

После изменения `p_` вызывается `replace`, удаляется запись истории, значение загружается и помещается в T2. Возвращается `false`: изменение политики не отменяет отсутствия значения до запроса.

### 5.4. Как replace выбирает список

Источник: [include/arc_cache.hpp, строки 28–39](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/include/arc_cache.hpp#L28-L39).

```cpp
    void replace(KeyT key) {
        if (!t1_counter_.empty() &&
            (t1_counter_.size() > p_ ||
             (b2_cache_.find(key) != b2_cache_.end() && t1_counter_.size() == p_))) {

            KeyT old_key = t1_counter_.back().first;

            t1_cache_.erase(old_key);
            t1_counter_.pop_back();

            b1_counter_.emplace_front(old_key);
            b1_cache_[old_key] = b1_counter_.begin();
```

Удаление из T1 происходит, если T1 превышает цель `p_`. Дополнительный случай — обращение к B2 при размере T1, точно равном цели. Вытесненный ключ сохраняется в B1.

Иначе, если T2 непуст, удаляется его последний объект, а ключ сохраняется в B2.

В каждом списке выбирается конец: самый старый элемент согласно порядку этого списка.

### 5.5. Совсем новый ключ и ограничения истории

Источник: [include/arc_cache.hpp, строки 120–123](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/include/arc_cache.hpp#L120-L123).

```cpp
        size_t l1_size = t1_counter_.size() + b1_counter_.size();
        size_t whole_size = l1_size + t2_counter_.size() + b2_counter_.size();

        if (l1_size == capacity_) {
```

Здесь `l1_size` означает **размер T1 вместе с B1**. Это локальное имя внутри ARC, а не первый уровень многоуровневого кэша.

Перед вставкой нового ключа код контролирует размер значений и истории:

- Если `T1 + B1 == capacity`, а T1 меньше capacity, удаляется старая запись B1 и вызывается `replace`.
- Если T1 уже занимает весь кэш, удаляется его последний объект напрямую, без добавления в B1.
- В другой ветке при достаточном общем размере вызывается `replace`; если общий размер достиг `2 * capacity`, перед этим удаляется старая запись B2.

После подготовки новый объект вставляется в T1. Таким образом, история не растёт бесконечно: суммарное число записей четырёх списков ограничивается удвоенной ёмкостью, а значения занимают не более самой ёмкости.

### 5.6. Пример изменения p

Ёмкость `2`, запросы `1 2 1 3 2 1`.

| Запрос | Результат | p после запроса | T1 | T2 | B1 | B2 |
|---|---|---:|---|---|---|---|
| 1 | Промах | 0 | `1` | — | — | — |
| 2 | Промах | 0 | `2, 1` | — | — | — |
| 1 | Попадание в T1 | 0 | `2` | `1` | — | — |
| 3 | Промах | 0 | `3` | `1` | `2` | — |
| 2 | Промах, найден в B1 | 1 | `3` | `2` | — | `1` |
| 1 | Промах, найден в B2 | 0 | — | `1, 2` | `3` | — |

Итог: **1 попадание, 5 промахов**. Таблица показывает механизм адаптации: запрос к B1 увеличил `p`, а следующий запрос к B2 уменьшил его. Адаптация не означает, что каждый короткий пример обязательно даст больше попаданий, чем LRU.

## 6. LIRS: защита данных с повторным использованием

**LIRS — Low Inter-reference Recency Set:** политика старается защищать объекты, повторно используемые с небольшими интервалами, и выделяет ограниченную часть кэша для менее устойчивого потока данных.

В коде нет числового счётчика расстояния между каждым обращением. Вместо этого используются порядок в стеке, наличие ключа в истории и переходы между состояниями.

### 6.1. Какие состояния бывают

Источник: [include/lirs_cache.hpp, строки 166–176](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/include/lirs_cache.hpp#L166-L176).

```cpp
    enum page_status_t { LIR, RESIDENT_HIR, NON_RESIDENT_HIR };

    struct page_t {
        page_status_t status_;

        bool in_stack_ = false;
        bool in_queue_ = false;

        typename std::list<KeyT>::iterator stack_iter_;
        typename std::list<KeyT>::iterator queue_iter_;
    };
```

Три состояния:

- `LIR`: защищённый объект, значение находится в кэше;
- `RESIDENT_HIR`: объект менее защищённой группы, значение пока находится в кэше;
- `NON_RESIDENT_HIR`: значение уже удалено, но ключ ещё присутствует в истории стека.

Слово **resident** означает именно наличие значения в кэше.

`in_stack_` и `in_queue_` показывают принадлежность к служебным спискам. Итераторы позволяют изменить нужные узлы без поиска по всему списку.

### 6.2. Четыре основные структуры

| Поле | Роль |
|---|---|
| `cache_` | Реальные значения всех резидентных объектов |
| `pages_` | Статус и итераторы для известных ключей |
| `stack_`, стек S | Порядок обращений и часть истории; сверху недавно использованные ключи |
| `queue_`, очередь Q | Только resident HIR; из конца выбирается жертва |

Здесь слово «стек» не означает, что программа использует `std::stack`. Это `std::list`, из которого можно перемещать и удалять узлы по итераторам.

Один ключ может присутствовать одновременно в S, Q и таблицах. Это несколько служебных записей об одном значении, а не несколько копий самого значения в `cache_`.

### 6.3. Размеры групп

Источник: [include/lirs_cache.hpp, строки 8–10](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/include/lirs_cache.hpp#L8-L10).

```cpp
    lirs_cache_t(size_t capacity)
        : capacity_(capacity), lhirs_(capacity == 0 ? 0 : std::max<size_t>(1, capacity / 4)),
          llirs_(capacity_ - lhirs_) {}
```

Для положительной ёмкости около четверти мест выделяется под HIR, но не меньше одного. Остальные места предназначены для LIR.

При `capacity = 3`: `lhirs_ = 1`, `llirs_ = 2`. При `capacity = 1`: `lhirs_ = 1`, `llirs_ = 0`; защищённой LIR-части нет.

Новые объекты сначала заполняют LIR-часть. После её заполнения новые ключи поступают как resident HIR в начало S и Q. Если HIR-часть заполнена, перед вставкой вызывается `evict_hir()`.

### 6.4. Попадание в LIR

Узел переносится в начало S, затем вызывается `prune_stack()`. Статус остаётся LIR, значение не загружается. Возвращается `true`.

Перемещение показывает, что объект снова использовался недавно. Очистка стека удаляет ненужную историю с его нижней границы.

### 6.5. Попадание в resident HIR

Значение уже есть, поэтому это попадание. Дальнейшее действие зависит от наличия ключа в S:

Источник: [include/lirs_cache.hpp, строки 79–92](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/include/lirs_cache.hpp#L79-L92).

```cpp
            // HIR is in stack S -> it becomes LIR
            if (page.in_stack_) {

                queue_.erase(page.queue_iter_);
                page.in_queue_ = false;

                page.status_ = LIR;
                lir_size_++;

                stack_.splice(stack_.begin(), stack_, page.stack_iter_);
                page.stack_iter_ = stack_.begin();

                demote_bottom_lir();
                prune_stack();
```

Если ключ ещё находится в S, его повторное использование считается основанием для повышения до LIR. Он удаляется из Q, перемещается наверх S, а `demote_bottom_lir()` переводит нижний LIR-объект в resident HIR, чтобы освободить место в защищённой группе.

Если ключ отсутствует в S, он пока остаётся HIR. Его добавляют наверх S и перемещают в начало Q. Если вскоре он будет запрошен снова, пока остаётся в S, уже сработает повышение.

### 6.6. Обращение к non-resident HIR

Это промах: в `cache_` значения нет. Код загружает значение и при необходимости удаляет жертву из Q.

Затем ключ становится LIR, переносится наверх S; нижний LIR переводится в HIR и стек очищается снизу. Здесь история сыграла роль сигнала для повышения, но результат запроса остаётся `false`.

### 6.7. Как удаляется значение

Источник: [include/lirs_cache.hpp, строки 178–200](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/include/lirs_cache.hpp#L178-L200).

```cpp
    void evict_hir() {

        if (queue_.empty())
            return;

        KeyT key = queue_.back();
        auto page_iter = pages_.find(key);
        auto &page = page_iter->second;

        queue_.pop_back();
        page.in_queue_ = false;

        cache_.erase(key);
        size_--;

        // if HIR is still in S, save it as non-resident HIR
        if (page.in_stack_) {
            page.status_ = NON_RESIDENT_HIR;
            return;
        }

        // HIR which is neither in S nor resident is a new element again
        pages_.erase(page_iter);
```

Жертва — последний элемент Q. Значение удаляется из `cache_`, размер резидентной части уменьшается.

Если ключ ещё есть в S, запись сохраняется как `NON_RESIDENT_HIR`. Если в S его уже нет, запись удаляется и из `pages_`: следующее обращение будет обработано как к совсем новому объекту.

### 6.8. Зачем нужна очистка стека

Источник: [include/lirs_cache.hpp, строки 223–243](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/include/lirs_cache.hpp#L223-L243).

```cpp
    void prune_stack() {

        // HIR cannot be at the bottom of stack S
        while (!stack_.empty()) {

            KeyT key = stack_.back();
            auto page_iter = pages_.find(key);
            auto &page = page_iter->second;

            if (page.status_ == LIR)
                return;

            stack_.pop_back();
            page.in_stack_ = false;

            // resident HIR remains only in Q
            if (page.status_ == RESIDENT_HIR)
                continue;

            // non-resident HIR outside S and Q becomes completely new
            pages_.erase(page_iter);
```

Функция удаляет HIR-записи с нижнего края S, пока не встретит LIR или пока стек не станет пустым.

- Resident HIR, удалённый из S, продолжает жить в Q и в `cache_`. Его значение не удаляется.
- Non-resident HIR, удалённый из S, теряет последнюю нужную запись истории; его удаляют из `pages_`.
- LIR останавливает очистку.

Так поддерживается правило: непустой стек после очистки заканчивается LIR-объектом.

### 6.9. Пример переходов

Ёмкость `3`, запросы `1 2 3 4 3 1 1`. Первые два ключа заполняют LIR-часть, для HIR остаётся одно место.

Обозначения в таблице: `L` — LIR, `H` — resident HIR, `G` — non-resident HIR. Слева верх S и начало Q.

| Запрос | Результат и действие | S | Q |
|---|---|---|---|
| 1 | Промах; первый LIR | `1L` | — |
| 2 | Промах; второй LIR | `2L, 1L` | — |
| 3 | Промах; новый HIR | `3H, 2L, 1L` | `3` |
| 4 | Промах; значение 3 вытеснено | `4H, 3G, 2L, 1L` | `4` |
| 3 | Промах по истории; 3 повышен, 1 понижен | `3L, 4G, 2L` | `1` |
| 1 | Попадание; 1 возвращён в S, остаётся HIR | `1H, 3L, 4G, 2L` | `1` |
| 1 | Попадание; 1 повышен, 2 понижен | `1L, 3L` | `2` |

Итог: **2 попадания, 5 промахов**. На пятом запросе значение `4` было удалено из Q, а значение `1` осталось в кэше, хотя ключ `1` после понижения удалился из S.

На последнем запросе очистка убрала снизу `2H`, затем `4G`, остановившись на `3L`. Значение `2` осталось в Q, а история `4` исчезла полностью.

### 6.10. Особенность памяти и времени

В этой реализации нет отдельного жёсткого лимита длины S. Пока нижний LIR не меняется, над ним могут накапливаться записи истории. Поэтому ограничение числа значений `capacity` не означает такого же ограничения всей служебной памяти LIRS.

`prune_stack()` содержит цикл и за один вызов может удалить много записей. Удаления распределяются по ранее накопленной истории, но обещать постоянное время каждого отдельного запроса нельзя.

## 7. IDEAL: знание будущих запросов

IDEAL получает всю последовательность заранее. При полном кэше он удаляет объект, следующее использование которого находится дальше всего в будущем. Если объект больше не нужен, он — подходящий кандидат на удаление.

Это правило Белади, также называемое MIN. Оно служит ориентиром: сколько попаданий можно получить при идеальном знании будущего в модели одинаковых по размеру объектов, пустого начального кэша и обязательной загрузки запрошенного объекта при промахе.

### 7.1. Почему это функция, а не lookup_update

Объявление находится в `include/ideal_cache.hpp`, определение — в `src/ideal_cache.cpp`.

`ideal_cache_hits` принимает `const std::vector<KeyT> &data` и `size_t capacity`, возвращает общее число попаданий. Массив запросов не является полем структуры; он существует у вызывающей стороны и передаётся по константной ссылке, без копирования всего вектора.

Обычный онлайн-кэш получает один текущий ключ. Для IDEAL этого недостаточно: без оставшейся последовательности нельзя выбрать самое далёкое следующее обращение.

### 7.2. Первый проход: ближайшее следующее использование

Источник: [src/ideal_cache.cpp, строки 12–21](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/src/ideal_cache.cpp#L12-L21).

```cpp
    std::vector<size_t> next_use(data.size(), data.size());
    std::unordered_map<KeyT, size_t> next_positions;

    for (size_t i = data.size(); i > 0;) {
        --i;
        auto next_iter = next_positions.find(data[i]);
        if (next_iter != next_positions.end())
            next_use[i] = next_iter->second;

        next_positions[data[i]] = i;
```

`next_use[i]` — индекс следующего появления ключа `data[i]`. Если следующего появления нет, используется число `data.size()`, которое больше любого допустимого индекса.

Проход идёт справа налево. Таблица `next_positions` хранит ближайшую уже встреченную позицию ключа справа. Сначала она используется для заполнения `next_use[i]`, затем обновляется текущим индексом.

Для `1 2 3 1 2 3`:

| Индекс i | Ключ | next_use[i] |
|---:|---:|---:|
| 0 | 1 | 3 |
| 1 | 2 | 4 |
| 2 | 3 | 5 |
| 3 | 1 | 6: больше не нужен |
| 4 | 2 | 6: больше не нужен |
| 5 | 3 | 6: больше не нужен |

### 7.3. Второй проход: моделирование кэша

В локальной таблице `cache` лежит соответствие «ключ — индекс его следующего использования». Сами значения для подсчёта попаданий не нужны.

Источник: [src/ideal_cache.cpp, строки 28–33](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/src/ideal_cache.cpp#L28-L33).

```cpp
    for (size_t i = 0; i < data.size(); i++) {
        auto cache_iter = cache.find(data[i]);
        if (cache_iter != cache.end()) {
            hits++;
            cache_iter->second = next_use[i];
            continue;
```

При попадании увеличивается `hits`, а позиция будущего обращения обновляется. Это необходимо: прежняя позиция уже наступила, и теперь нас интересует следующая.

При полном кэше на промахе выбирается максимальная позиция:

Источник: [src/ideal_cache.cpp, строки 36–46](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/src/ideal_cache.cpp#L36-L46).

```cpp
        if (cache.size() == capacity) {
            auto deleting_iter = cache.begin();
            for (auto it = cache.begin(); it != cache.end(); it++) {
                if (it->second > deleting_iter->second)
                    deleting_iter = it;
            }

            cache.erase(deleting_iter);
        }

        cache.emplace(data[i], next_use[i]);
```

Здесь выполняется полный проход по текущим ключам кэша. После удаления жертвы вставляется новый ключ с его будущей позицией.

Если несколько ключей больше не понадобятся, удаление любого из них одинаково хорошо для числа попаданий. Конкретный выбор может зависеть от порядка обхода `unordered_map`.

### 7.4. Пошаговый пример

Ёмкость `2`, запросы `1 2 3 1 2 3`.

| Индекс | Ключ | Решение | Ключи в кэше после запроса |
|---:|---:|---|---|
| 0 | 1 | Промах, вставить | `{1}` |
| 1 | 2 | Промах, вставить | `{1, 2}` |
| 2 | 3 | Промах; 2 нужен позже, чем 1, удалить 2 | `{1, 3}` |
| 3 | 1 | Попадание; больше обращений к 1 нет | `{1, 3}` |
| 4 | 2 | Промах; удалить больше не нужный 1 | `{2, 3}` |
| 5 | 3 | Попадание | `{2, 3}` |

Итог: **2 попадания, 4 промаха**. При той же ёмкости обычный LRU на этой последовательности даёт 0 попаданий: цикл состоит из трёх ключей, а мест только два.

### 7.5. Почему правило оптимально

Представим, что кэш заполнен и нужно выбрать жертву. Один алгоритм удаляет объект A, который понадобится раньше, а IDEAL удаляет B, который понадобится позже.

До следующего обращения к A сохранение A вместо B не мешает обслуживать запросы: B до этого момента всё равно не нужен. В момент обращения к A сохранённый A может избежать промаха. Это позволяет заменить решение другой стратегии выбором IDEAL без увеличения числа промахов; повторение такого рассуждения даёт оптимальность.

Утверждение относится к описанной модели. Если учитывать разные размеры объектов, стоимость загрузки или другую схему допуска в кэш, постановка задачи меняется.

## 8. Многоуровневый кэш

Многоуровневый кэш — это организация нескольких политик, а не ещё одно правило выбора жертвы. Каждый уровень самостоятельно решает, какие значения хранить.

В проекте есть две реализации: динамическая иерархия для `cache_runner` и шаблонная обёртка для двух заранее созданных кэшей.

### 8.1. Произвольное количество уровней

Основные файлы — `include/cache_hierarchy.hpp` и `src/cache_hierarchy.cpp`. Конструктор принимает вектор конфигураций: у каждого уровня есть строка `policy` и число `capacity`.

В зависимости от строки создаётся LRU, LFU, 2Q, ARC или LIRS. IDEAL не включён в этот набор: текущий интерфейс обрабатывает одиночные запросы без доступа к будущему.

### 8.2. Как разные типы хранятся в одном векторе

Обычный `std::vector<lru_cache_t<...>>` не может одновременно хранить объект LFU. Поэтому введён общий базовый тип `level_t` с виртуальным `lookup_update`, а для каждой конкретной политики создаётся адаптер:

Источник: [src/cache_hierarchy.cpp, строки 11–19](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/src/cache_hierarchy.cpp#L11-L19).

```cpp
template <typename Cache>
struct cache_hierarchy_t::level_impl_t : level_t {
    explicit level_impl_t(size_t capacity) : cache(capacity) {}

    bool lookup_update(size_t key) override {
        return cache.lookup_update(key, [](size_t requested_key) { return requested_key; });
    }

    Cache cache;
```

Адаптер хранит настоящий объект `Cache` и приводит его интерфейс к единому виду `lookup_update(size_t key)`. Функция-загрузчик возвращает ключ как значение.

Сами уровни хранятся так:

Источник: [include/cache_hierarchy.hpp, строки 36–39](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/include/cache_hierarchy.hpp#L36-L39).

```cpp
  std::vector<std::unique_ptr<level_t>> caches_;
  std::vector<cache_level_stats_t> stats_;
  size_t requests_ = 0;
  size_t memory_accesses_ = 0;
```

`unique_ptr` означает единоличное владение: при уничтожении иерархии принадлежащие ей уровни удаляются автоматически. Через указатель на базовый класс виртуальный вызов попадает в адаптер нужной политики.

### 8.3. Как проходит один запрос

Источник: [src/cache_hierarchy.cpp, строки 45–55](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/src/cache_hierarchy.cpp#L45-L55).

```cpp
bool cache_hierarchy_t::lookup_update(size_t key) {
    requests_++;
    for (size_t i = 0; i < caches_.size(); i++) {
        if (caches_[i]->lookup_update(key)) {
            stats_[i].hits++;
            return true;
        }
        stats_[i].misses++;
    }
    memory_accesses_++;
    return false;
```

Последовательность действий:

1. Увеличивается общее число запросов.
2. Проверяется L1. При попадании увеличивается его счётчик, обработка сразу заканчивается.
3. При промахе L1 увеличивается его счётчик промахов и проверяется L2.
4. Так продолжается до первого попадания либо до конца списка уровней.
5. Если промахнулись все уровни, увеличивается `memory_accesses_`, возвращается `false`.

**L2 не получает запросы, завершившиеся попаданием в L1.** Поэтому его частоты LFU или порядок LRU отражают отфильтрованную последовательность, а не все запросы пользователя.

### 8.4. Когда значения вставляются на верхние уровни

Каждый вызванный `lookup_update` при промахе сам вставляет значение, если его ёмкость положительна. В динамической иерархии верхний уровень делает это до проверки нижнего: его загрузчик просто возвращает ключ.

Это подходит для подсчёта попаданий в принятой модели. Но здесь нет передачи настоящего значения из L2 в L1 после чтения памяти. Для работы с реальными данными интерфейса, возвращающего только `bool`, было бы недостаточно: пришлось бы также передавать значение и согласовывать его загрузку.

При попадании в L2 верхние уровни, на которых были промахи, уже получили объект. Уровни ниже L2 этот запрос вообще не видят.

### 8.5. Независимость уровней и дубликаты

Один ключ может одновременно находиться в нескольких уровнях. Вытеснение из L2 не вызывает автоматического удаления из L1. Также вставка в L1 не удаляет копию из L2.

Поэтому эта модель не гарантирует ни включение всего L1 в L2, ни отсутствие одинаковых ключей между уровнями. Сумма ёмкостей — число мест для значений, но число **различных** сохранённых ключей может быть меньше из-за дубликатов.

### 8.6. Маленький пример

L1 — LRU ёмкости `1`, L2 — LFU ёмкости `2`. Запросы: `1 2 1 2`.

| Запрос | L1 | L2 | Обращение к памяти |
|---|---|---|---|
| 1 | Промах, вставлен 1 | Промах, вставлен 1 | Да |
| 2 | Промах, 1 заменён на 2 | Промах, вставлен 2 | Да |
| 1 | Промах, 2 заменён на 1 | Попадание | Нет |
| 2 | Промах, 1 заменён на 2 | Попадание | Нет |

Итог: L1 — `0` попаданий и `4` промаха; L2 — `2` попадания и `2` промаха; вся иерархия — **2 попадания, 2 обращения к памяти**.

При добавлении ещё одного запроса `2` получится попадание в L1. Статистика L2 на этом запросе не изменится.

### 8.7. Как проверять статистику

Для любого завершённого прогона:

- `requests = hits_total + memory_accesses`;
- `hits_total = hits_L1 + hits_L2 + ...`;
- `hits_L1 + misses_L1 = requests`;
- число запросов к следующему уровню равно числу промахов предыдущего;
- промахи последнего уровня равны обращениям к памяти.

Суммировать промахи всех уровней для получения общего числа промахов нельзя: один пользовательский запрос может дать промах сразу на нескольких уровнях.

В программе общий результат вычисляется именно через обращения к памяти:

Источник: [src/cache_runner.cpp, строки 101–102](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/src/cache_runner.cpp#L101-L102).

```cpp
void print_results(const cache_hierarchy_t &cache, bool json) {
    const size_t hits = cache.requests() - cache.memory_accesses();
```

Обычный вывод — одно число попаданий всей иерархии. Режим `--json` дополнительно показывает общие промахи и счётчики отдельных уровней.

### 8.8. Откуда берутся ёмкости уровней

Файл `.cfg` по-прежнему задаёт только число уровней и политики, например:

```text
3 LRU ARC LIRS
```

Общая ёмкость берётся из первого числа файла запросов. Размеры уровней вычисляет `make_levels()`, которая теперь вынесена из `cache_runner.cpp` в отдельный `src/cache_config.cpp`. Её объявление:

Источник из итогового патча: [include/cache_config.hpp](../include/cache_config.hpp), строки 8–11.

```cpp
std::vector<cache_level_config_t> make_levels(
    const std::vector<std::string> &policies, size_t capacity,
    const std::string &distribution = "geometric", size_t ratio = 2,
    const std::vector<size_t> &sizes = {});
```

Если параметры не указаны, используются `distribution = "geometric"` и `ratio = 2`: веса уровней равны `1, 2, 4, ...`. Это изменение поведения по умолчанию. Для двух уровней доли остались прежними — `1/3` и `2/3`, а для трёх стали `1/7`, `2/7`, `4/7`.

| Параметры | Веса | Размеры при общей ёмкости 21 |
|---|---|---|
| `--distribution equal` | `1, 1, 1` | `7, 7, 7` |
| `--distribution linear` | `1, 2, 3` | `3, 7, 11` |
| `--distribution geometric` | `1, 2, 4` | `3, 6, 12` |
| `--ratio 4` | `1, 4, 16` | `1, 4, 16` |
| `--sizes 1,5,15` | Точные размеры | `1, 5, 15` |

**Равномерное распределение** подходит, когда нужно выделить одинаковое число мест всем уровням. **Линейное** сохраняет старый вариант. **Геометрическое** делает каждый следующий вес в `ratio` раз больше предыдущего. Множитель целый и должен быть не меньше 2.

В коде веса строятся так:

Источник из итогового патча: [src/cache_config.cpp](../src/cache_config.cpp), строки 42–50.

```cpp
        for (size_t i = 0; i < policies.size(); i++) {
            size_t weight = distribution == "equal" ? 1 : i + 1;
            if (distribution == "geometric") {
                if (i)
                    geometric_weight = checked_multiply(geometric_weight, ratio);
                weight = geometric_weight;
            }
            weights.push_back(weight);
            sum = checked_add(sum, weight);
```

`geometric_weight` начинается с единицы. На каждом последующем уровне он умножается на `ratio`. `checked_multiply` и `checked_add` проверяют переполнение: если результат не помещается в `size_t`, программа выдаёт ошибку вместо получения неверных размеров.

После вычисления весов распределяется общий бюджет:

Источник из итогового патча: [src/cache_config.cpp](../src/cache_config.cpp), строки 52–60.

```cpp
        size_t remaining = capacity;
        for (size_t i = 0; i < weights.size(); i++) {
            // Last level receives the rounding remainder; no slots are lost.
            size_t size = remaining;
            if (i + 1 != weights.size())
                size = (capacity / sum) * weights[i]
                     + checked_multiply(capacity % sum, weights[i]) / sum;
            capacities.push_back(size);
            remaining -= size;
```

Для всех уровней, кроме последнего, берётся целая часть `capacity * weight / sum`. Выражение разбито через частное и остаток, чтобы не выполнять прямое произведение всей ёмкости на вес. Последний уровень получает `remaining` — всё, что осталось после предыдущих.

Например, для ёмкости `22` и весов `1, 2, 4` размеры будут `3, 6, 13`. Округление не теряет места. Из-за остатка фактические размеры не всегда образуют точную геометрическую прогрессию.

`--sizes` позволяет задать размеры без весов. Число размеров должно совпасть с числом политик, а сумма — с общей ёмкостью из входного файла. Например, при общей ёмкости `21` допустимо `--sizes 1,5,15`. Если сумма равна `20`, программа сообщит об ошибке.

Формат `.cfg` не расширен размерами: точные размеры задаются аргументом запуска. В самом C++ классе по-прежнему можно непосредственно передать вектор `cache_level_config_t`.

В новой функции распределения многоуровневая конфигурация с пустым уровнем отклоняется. Если маленький бюджет при геометрическом распределении дал L1 размером ноль, нужно увеличить бюджет, выбрать другое распределение или передать положительные размеры через `--sizes`. Сам `cache_hierarchy_t` не переписывался; проверка относится к созданию конфигурации для runner. Одиночный кэш ёмкости ноль остаётся доступным как граничный случай.

Для выбора настраиваемого роста достаточно одного примера: в [характеристиках AMD Ryzen 9 9950X](https://www.amd.com/en/products/processors/desktops/ryzen/9000-series/amd-ryzen-9-9950x.html) указаны суммарные L1/L2/L3 размером `1280 KB`, `16 MB`, `64 MB`. Это показывает, что старое `1:2:3` не является универсальным ориентиром. Приведены суммарные размеры процессора, а не размеры на одном пути конкретного ядра. Множитель 2 в программе — удобная начальная настройка эксперимента, а не точная модель этого процессора.

### 8.9. Отдельная двухуровневая обёртка

В `include/multilevel_cache.hpp` есть `multilevel_cache_t<L1Cache, L2Cache>`. Она хранит ссылки на два уже созданных кэша и требует, чтобы ёмкость L1 была строго меньше ёмкости L2.

Здесь переход к L2 оформлен через загрузчик верхнего уровня:

Источник: [include/multilevel_cache.hpp, строки 21–40](https://github.com/demonsofya/cache-realisation/blob/8d147bb2a0cd85d7b0bb9c708c190fb93a5bead6/include/multilevel_cache.hpp#L21-L40).

```cpp
        auto load_from_l2 = [&](KeyT requested_key) {
            l2_accessed = true;
            l2_hit = l2_.lookup_update(requested_key, [&](KeyT memory_key) {
                memory_accesses_++;
                return slow_get_value(memory_key);
            });
            hits_l2_ += l2_hit;

            // lookup_update returns only bool; in this simulator value == key.
            return requested_key;
        };

        bool l1_hit = l1_.lookup_update(key, load_from_l2);
        hits_l1_ += l1_hit;

        // Existing caches do not call their loader when capacity is zero.
        if (!l1_hit && !l2_accessed)
            load_from_l2(key);

        return l1_hit || l2_hit;
```

При промахе L1 вызывает `load_from_l2`. Та проверяет L2; если и там промах, внутренний загрузчик увеличивает `memory_accesses_` и вызывает исходный `slow_get_value`.

Флаг `l2_accessed` нужен для случая нулевой ёмкости L1. Такой L1 не вызывает загрузчик, поэтому после его ответа обёртка сама обращается к L2.

`hits_l1_` и `hits_l2_` считают попадания отдельно; возвращаемое `l1_hit || l2_hit` показывает, удалось ли обслужить запрос хотя бы на одном уровне.

Обёртка также предполагает, что значение равно ключу: из L2 возвращается только `bool`, поэтому загрузчик L1 возвращает `requested_key`. Оба переданных кэша должны жить дольше обёртки. Их не следует параллельно использовать отдельно от неё, иначе статистика и предположения об общем потоке запросов перестанут соответствовать друг другу.

## 9. Сравнение правил и стоимости

Пусть `C` — ёмкость одного кэша, `N` — длина последовательности, `H` — число хранимых записей истории LIRS. Оценки ниже предполагают среднюю постоянную стоимость операций хеш-таблицы и фиксированную стоимость работы с ключом и значением. Стоимость внешней загрузки не включена.

| Политика | Что определяет вытеснение | Стоимость обработки | Память |
|---|---|---|---|
| LRU | Самое старое последнее обращение | В среднем O(1) на запрос | O(C) |
| LFU в проекте | Минимальная частота; равенства разрешаются порядком списка | До O(C) на попадание из-за проходов | O(C) |
| 2Q | FIFO в A1in либо LRU в Am | В среднем O(1) на запрос | O(C), включая ограниченную историю |
| ARC | Конец T1 или T2 с учётом p и истории | В среднем O(1) на запрос | O(C), включая ограниченную историю |
| LIRS в проекте | Конец Q; S управляет повышениями и понижениями | Базовые операции O(1); отдельная очистка может пройти по множеству записей | O(C + H), отдельного лимита H нет |
| IDEAL в проекте | Самое далёкое следующее использование | Подготовка O(N); весь прогон до O(N · C) из-за поиска жертвы | O(N + min(C, N)) |

Для иерархии стоимость одного запроса складывается из стоимости посещённых уровней. При попадании в L1 нижние уровни не вызываются. При промахе на всех уровнях нужно обработать весь их список.

Хеш-таблица не даёт безусловной гарантии O(1) в худшем случае. Таблица описывает обычную ожидаемую стоимость выбранных структур, а не максимальное время при любых коллизиях.

## 10. Как читать результаты экспериментов

### 10.1. Какие свойства входа важны

| Характер запросов | Что проверяет такой сценарий |
|---|---|
| Много повторов небольшого набора | Умещается ли рабочий набор и остаются ли только начальные промахи |
| Один популярный ключ среди новых | Умеет ли политика защищать часто используемые данные |
| Длинное чтение без повторов | Не засоряет ли поток одноразовых данных защищённую часть |
| Возврат к прежнему набору после сканирования | Сохранились ли значения или полезная история |
| Резкая смена популярного набора | Как быстро политика перестаёт защищать старые интересы |
| Цикл длиной чуть больше ёмкости | Как правило вытеснения ведёт себя при постоянном переполнении |
| Смешение коротких всплесков и долгой популярности | Насколько удачно сочетаются давность, частота и история |

Эти сценарии можно связать с просмотром страниц, чтением каталога, обращениями к популярным записям или сменой пользовательской сессии. Но синтетическая последовательность — это модель поведения, а не измерение реальной аудитории.

### 10.2. Почему нельзя выбрать победителя по одному тесту

LFU может хорошо удерживать постоянно популярные ключи, но медленно освобождать место после смены интересов. LRU быстро реагирует на новое, но может потерять полезные данные во время сканирования. 2Q, ARC и LIRS используют дополнительные структуры, чтобы различать такие ситуации, однако их результат тоже зависит от входа.

Разделение общей ёмкости между уровнями само по себе не гарантирует большего числа попаданий. Часть мест занята одинаковыми ключами, а нижний LFU видит только промахи верхнего кэша. Популярность в этом отфильтрованном потоке может отличаться от популярности во всём входе.

IDEAL полезен как ориентир для одного кэша той же ёмкости в той же модели допуска данных. В сравнениях проекта он показывает, насколько решения без знания будущего отличаются от оптимального выбора жертвы. Его число попаданий не означает, что такая политика доступна реальной системе онлайн.

### 10.3. Что проверено для примеров этого документа

Все шесть последовательностей из разделов LRU, LFU, 2Q, ARC, LIRS и IDEAL выполнены с исходными C++ реализациями указанной версии. Также выполнен пример двух уровней LRU(1) + LFU(2).

| Пример | Ёмкость | Запросов | Попаданий | Промахов всей системы |
|---|---:|---:|---:|---:|
| LRU: `1 2 3 1 4 2` | 3 | 6 | 1 | 5 |
| LFU: `1 2 3 1 4 2` | 3 | 6 | 2 | 4 |
| 2Q: `1 2 3 1 4 1 1` | 3 | 7 | 2 | 5 |
| ARC: `1 2 1 3 2 1` | 2 | 6 | 1 | 5 |
| LIRS: `1 2 3 4 3 1 1` | 3 | 7 | 2 | 5 |
| IDEAL: `1 2 3 1 2 3` | 2 | 6 | 2 | 4 |
| LRU(1) + LFU(2): `1 2 1 2` | 3 суммарно | 4 | 2 | 2 |

Это проверка учебных примеров, а не полный аудит корректности всех алгоритмов на любых входах. Более широкий набор сравнений описан в [results.md](results.md), а команды сборки и запуска — в [README.md](../README.md).


## 11. Как теперь устроена сборка

### 11.1. Почему удалён scripts/build.py

Старый скрипт каждый раз запускал компилятор через `subprocess` с перечислением исходных файлов. Он не поддерживал собственный граф зависимостей и не определял, можно ли использовать уже собранные объектные файлы.

Теперь сборка полностью описана в `CMakeLists.txt`. CMake создаёт правила для выбранной системы сборки — например, Make или Ninja. При последующем `cmake --build` эта система проверяет изменения исходников и зависимостей. Если исходники не изменились, повторная компиляция не нужна.

Python-скрипты продолжают использовать `subprocess`, чтобы запускать готовую программу для разных данных. Это запуск эксперимента; сборкой занимается CMake.

### 11.2. Библиотеки и исполняемые файлы

Фрагмент актуального `CMakeLists.txt`:

Источник из итогового патча: [CMakeLists.txt](../CMakeLists.txt), строки 25–35.

```cmake
add_library(cache_headers INTERFACE)
target_include_directories(cache_headers INTERFACE "${CMAKE_CURRENT_SOURCE_DIR}/include")

add_library(cache_core src/cache_hierarchy.cpp src/cache_config.cpp src/ideal_cache.cpp)
target_link_libraries(cache_core PUBLIC cache_headers)

add_executable(cache_runner src/cache_runner.cpp)
target_link_libraries(cache_runner PRIVATE cache_core CLI11::CLI11)

add_executable(cache src/cache.cpp)
target_link_libraries(cache PRIVATE cache_core)
```

`cache_headers` — интерфейсная цель. У неё нет собственных объектных файлов, но она передаёт каталог заголовков тем целям, которые с ней связаны.

`cache_core` содержит общую компилируемую часть: иерархию, распределение размеров и IDEAL. Вместо повторного перечисления этих файлов в нескольких исполняемых целях программы подключают одну библиотеку.

Связь `PUBLIC cache_headers` означает, что каталог заголовков нужен и самой `cache_core`, и её потребителям. Поэтому `cache_runner`, связанный с `cache_core`, также видит заголовки проекта.

`cache_runner` — основная программа для одного конфига и потока запросов. `cache` — прежняя демонстрационная программа, которая сравнивает несколько политик и печатает подписанные результаты. Новые параметры распределения относятся к `cache_runner`.

### 11.3. Зависимости и тесты

CLI11 — библиотека разбора аргументов командной строки. GoogleTest используется для C++ тестов. CMake сначала ищет установленные пакеты; если их нет и `CACHE_FETCH_DEPENDENCIES=ON`, получает закреплённые Git-версии через `FetchContent`.

Это не скачивание произвольной последней версии: в `GIT_TAG` указаны конкретные хеши коммитов. Интернет нужен, если необходимые исходники ещё не получены и подходящие библиотеки не установлены.

`include(CTest)` создаёт опцию `BUILD_TESTING`. При её включении собирается `cache_tests`, подключается `GTest::gtest_main`, а `gtest_discover_tests` регистрирует отдельные GoogleTest-проверки в CTest.

При наличии Python регистрируется интеграционная проверка:

Источник из итогового патча: [CMakeLists.txt](../CMakeLists.txt), строки 63–65.

```cmake
        add_test(NAME RunnerIntegration
            COMMAND "${Python3_EXECUTABLE}" "${CMAKE_CURRENT_SOURCE_DIR}/scripts/test_cache_runner.py"
                    --binary $<TARGET_FILE:cache_runner>)
```

`$<TARGET_FILE:cache_runner>` подставляет путь к реально построенному исполняемому файлу. Поэтому тест не зависит от предположения, что файл всегда называется именно `build/cache_runner` и лежит относительно текущего каталога.

При `BUILD_TESTING=OFF` тестовая программа и GoogleTest не нужны. CLI11 по-прежнему необходим для `cache_runner`.

### 11.4. Остальная очистка

Удалены FIXME-комментарии. Имена наборов тестов изменены на `CommonCacheTest`, `TwoQCacheTest` и `ArcCacheTest`: без подчёркиваний, согласно правилам имён GoogleTest. В `src/cache.cpp` удалены FIXME-комментарии; его вычисления не переписывались.

README сокращён до назначения проекта, сборки, запуска и краткого списка скриптов. Подробные настройки вынесены в `docs/hierarchy.md`. `.gitignore` исключён из выданного патча по просьбе пользователя.

## 12. Как пользоваться обновлённой программой

### 12.1. Сборка и запуск тестов

Все команды выполняются из корня проекта после применения патча:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

Первая команда создаёт или обновляет настройки сборки, вторая строит цели, третья выполняет зарегистрированные проверки.

Для сборки без тестов:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DBUILD_TESTING=OFF
cmake --build build --parallel
```

Чтобы потом снова включить тесты, передай `-DBUILD_TESTING=ON`: значение опции сохраняется в CMake-кэше между запусками.

Если зависимости уже установлены в собственный префикс:

```bash
cmake -S . -B build -DCMAKE_PREFIX_PATH=/path/to/dependencies -DCACHE_FETCH_DEPENDENCIES=OFF
```

Указанный путь — корень установки библиотек. В нём обычно находятся подкаталоги `include` и `lib`. Если CMake не найдёт требуемый пакет и скачивание отключено, настройка завершится ошибкой.

### 12.2. Полный пример файлов

Создай `cache.cfg`:

```text
3 LRU ARC LIRS
```

Создай `requests.txt`:

```text
21 8
1 2 3 4 1 2 3 4
```

Общая ёмкость равна `21`, запросов `8`. Первая четвёрка обращений даёт промахи; повторная — попадания. При настройках по умолчанию ёмкости уровней равны `3, 6, 12`.

```bash
./build/cache_runner cache.cfg requests.txt
```

Ожидаемый вывод:

```text
4
```

С поуровневой статистикой:

```bash
./build/cache_runner cache.cfg requests.txt --json
```

`requests` — число входных запросов; `hits` — попадания всей системы; `misses` — промахи всех уровней с обращением к памяти; `levels` — массив статистики уровней.

### 12.3. Изменение размеров

```bash
./build/cache_runner cache.cfg requests.txt --distribution equal
./build/cache_runner cache.cfg requests.txt --distribution linear
./build/cache_runner cache.cfg requests.txt --distribution geometric --ratio 4
./build/cache_runner cache.cfg requests.txt --sizes 1,5,15 --json
```

Последняя команда задаёт размеры непосредственно. Нельзя одновременно передать `--sizes` и `--distribution` либо `--ratio`. Также нельзя явно передать `--ratio` вместе с равномерным или линейным распределением.

Без пути к файлу запросов runner читает стандартный ввод. Например:

```bash
./build/cache_runner cache.cfg --sizes 1,5,15 < requests.txt
```

### 12.4. Как CLI11 читает параметры

Объект `CLI::App` содержит описание программы и зарегистрированные параметры. `add_option` связывает аргумент с переменной, `add_flag` задаёт булев флаг, `check` добавляет проверку, а `excludes` запрещает несовместимые сочетания.

Источник из итогового патча: [src/cache_runner.cpp](../src/cache_runner.cpp), строки 115–118.

```cpp
    app.add_option("--sizes", sizes, "Exact capacities, comma-separated; sum must match input capacity")
        ->delimiter(',')->expected(1, -1)->check(CLI::NonNegativeNumber)
        ->excludes(distribution_option)->excludes(ratio_option);
    CLI11_PARSE(app, argc, argv);
```

`delimiter(',')` разбивает `1,5,15` на три числа. `CLI11_PARSE` запускает разбор; при `--help` библиотека выводит справку, а при ошибке аргументов — диагностическое сообщение.

```bash
./build/cache_runner --help
```

Остальные смысловые проверки выполняются в C++: сумма размеров, отсутствие пустых уровней, допустимость множителя. Проверка формата аргумента и проверка его смысла — разные этапы.

## 13. Python-скрипты и проверки

### 13.1. compare_caches.py: сравнение сохранённых сценариев

Скрипт читает `requests/comparison/scenarios.json`, находит соответствующие файлы запросов и проверяет согласованность числа запросов и ёмкости с описанием сценария.

Для каждого выбранного сценария он:

1. Вычисляет IDEAL своим Python-алгоритмом Белади.
2. Запускает `cache_runner` отдельно для LRU, LFU, 2Q, ARC и LIRS.
3. Запускает выбранную многоуровневую конфигурацию с тем же общим бюджетом.
4. Читает JSON, проверяет счётчики и сравнивает число попаданий с ориентиром IDEAL.
5. Печатает таблицу и при `--csv` сохраняет строки результатов.

Временные `.cfg` создаются через `tempfile.TemporaryDirectory`. После завершения работы временный каталог удаляется. Это позволяет пробовать разные политики без создания множества постоянных конфигов.

По умолчанию многоуровневый вариант — LRU+LFU, распределение геометрическое с множителем 2. Уровни независимы. Столбец `mode` со значением `independent` в CSV — описание текущего поведения, а не переключатель: опции `--mode` в итоговой версии нет.

```bash
python3 scripts/compare_caches.py --list
python3 scripts/compare_caches.py --scenario HotKeysAndScans
python3 scripts/compare_caches.py --csv results/comparison.csv
```

`--levels` выбирает политики произвольного числа уровней:

```bash
python3 scripts/compare_caches.py --levels LRU ARC LIRS --scenario PopularitySkewWithLongTail
```

`--all-pairs` вместо выбранного списка перебирает декартово произведение пяти политик с собой: всего 25 упорядоченных пар. LRU+LFU и LFU+LRU проверяются отдельно.

```bash
python3 scripts/compare_caches.py --all-pairs --distribution equal --csv results/equal.csv
python3 scripts/compare_caches.py --all-pairs --ratio 4 --csv results/geometric.csv
```

Если выбранное распределение даёт пустой уровень, скрипт выводит причину пропуска и продолжает остальные сравнения. Пропуск не записывается как нулевой результат: конфигурация просто не выполнялась.

В CSV есть сценарий, общий бюджет, число запросов, название конфигурации, распределение, множитель, попадания, промахи, размеры и попадания отдельных уровней. Поля записываются через `csv.DictWriter`, разделитель по умолчанию `;`. Например, `--delimiter ,` выбирает запятую.

### 13.2. run_benchmarks.py: свои конфиги и запросы

Этот скрипт получает готовые файлы через `--configs` и `--requests`, а затем запускает каждое сочетание «конфиг — файл запросов». Например, два конфига и три входных файла дают шесть запусков программы.

Он передаёт в runner `--distribution`, `--ratio` либо `--sizes`, добавляет `--json`, разбирает результат и создаёт общую таблицу. В отличие от `compare_caches.py`, он не добавляет IDEAL и не создаёт автоматически все политики.

Пример с файлами из проекта:

```bash
python3 scripts/run_benchmarks.py --configs configs/three_levels.cfg --requests requests/comparison/PopularitySkewWithLongTail_24.txt --sizes 2,6,16 --csv results/custom.csv
```

Если передать несколько файлов, явные размеры должны подходить ко всем сочетаниям: совпадать по числу уровней и по сумме с общим бюджетом каждого входа. Для разных бюджетов удобнее использовать распределение.

В текущем Python-скрипте указание `--sizes` имеет приоритет: при нём в runner передаются только точные размеры. Прямой C++ интерфейс строже и отвергает совместное указание `--sizes` с параметрами распределения.

### 13.3. generate_requests.py: генерация входа

Этот файл в последнем патче не менялся. Он генерирует последовательности запросов и сохраняет их в текстовом формате runner. Параметр `--capacity` задаёт общий бюджет во входном файле, `--seed` делает генерацию воспроизводимой, `--output-dir` выбирает каталог вывода.

```bash
python3 scripts/generate_requests.py --capacity 21 --seed 2026 --output-dir requests/generated
```

Генерация не собирает и не запускает C++ программу. Полученные файлы затем передаются в runner или `run_benchmarks.py`.

### 13.4. test_cache_runner.py: проверка внешнего поведения

Это интеграционные тесты: они запускают готовую программу как отдельный процесс и проверяют ввод, аргументы и вывод. Путь теперь выбирается параметром `--binary`, вместо переменной окружения `CACHE_RUNNER`:

```bash
python3 scripts/test_cache_runner.py --binary build/cache_runner
```

Проверяются чтение из файла и stdin, числовой вывод, JSON, корректность счётчиков, все пять политик, варианты распределения, неверные файлы и параметры, справка `--help`. Среди неправильных параметров проверяется и `--mode`: такой опции в текущей версии нет.

Скрипт создаёт временные файлы, запускает runner через `subprocess.run` и проверяет код завершения и содержимое потоков. Он не проверяет внутренние списки C++ кэшей — для внутренних правил используются GoogleTest-тесты.

### 13.5. Что было проверено после изменения

Новый `test/config_tests.cpp` проверяет конкретные размеры при разных распределениях, сохранение бюджета после округления, явные размеры, недопустимые конфигурации и переполнение арифметики.
